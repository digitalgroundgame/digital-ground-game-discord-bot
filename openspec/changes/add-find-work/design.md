# Design

## Context

The work already exists on the `give-issue-pr-review` branch, with the fixes from the code review of #189 landing in #190. This change records it in OpenSpec rather than proposing something new, so the design describes the choices the code made and why.

## Goals / Non-Goals

**Goals:**

- Point members at work they are likely able to do, plus one nudge toward neglected work.
- Make every payout attributable to the Discord member who took the work.
- Never pay twice for the same claim, and never lose a payout to a GitHub outage.

**Non-Goals:**

- Matching on Discord roles or skill labels. An earlier draft slugged every Discord role name against issue labels, which let unrelated roles such as a city or a squad match and needed labels kept in sync with role names.
- Weighting the wildcard by how few members are on the teams that reach a repository (staleness stands in for now).
- Raising GitHub access requests automatically when a member can't be assigned.
- Enumerating private repositories.

## Decisions

- **Curation by label on GitHub.** An issue is offered only while it carries an opt-in label, so maintainers advertise or withdraw work on GitHub without touching bot config. The alternative, a list in config, would drift.
- **Several opt-in labels, not one.** A single bespoke `available` label is friction: if nobody remembers to apply it, the pool stays empty and `/find-work` offers nothing. `good first issue` and `help wanted` are GitHub's standard labels for the same intent, and repositories already apply them, so accepting them fills the pool with no extra work while still needing a person to opt each issue in. The alternatives were rejected: offering every unassigned issue unless it carries an opt-out label would hand newcomers vague ideas, untriaged bugs and tracking issues, and make trivial self-filed issues an easy way to farm points; opting whole repositories in from config would drift like any config list. Which opt-in label an issue carries makes no difference to the draw or the payout.
- **One query per label.** GitHub's issues endpoint combines a comma-separated `labels` filter with AND, so a single request can't ask for any of several labels. The pool refresh runs one paged query per opt-in label per repository and merges the results by issue number. With three labels that is three requests per repository each hour, well inside the hourly budget. Fetching every open, unassigned issue and filtering locally was rejected: it pages through unlabelled issues, and the 10-page cap could cut off labelled ones in a busy repository. Because commas separate labels in that filter, a label name containing one is rejected at startup.
- **Retired key fails loudly.** The setting changes from `markerLabel` (one string) to `markerLabels` (a list). The feature hasn't shipped, so there is no compatibility shim, but a leftover `markerLabel` stops startup rather than being ignored: ignoring it would silently replace a custom label with the defaults.
- **Cached pools refreshed by jobs.** The command reads from in-memory caches loaded at startup and refreshed hourly, so a draw costs no GitHub calls and stays fast. Because the cache can be up to an hour old, a claim re-reads the issue on GitHub before assigning, so a member never lands as a second assignee beside someone who took the issue in the meantime.
- **Only the wildcard slot is a wildcard.** The flag sets the payout rate, so only the card drawn into the wildcard slot carries it. Backfilled cards pay the ordinary rate even when they're outside the member's team repositories; otherwise a member whose teams match nothing would earn the wildcard rate on every claim.
- **Matched by GitHub team repositories.** A member's matched issues are those in repositories their GitHub teams reach. Team membership is what `/grant-access` hands out, and the org's teams map closely onto its repositories, so this needs no labels beyond the opt-in ones and no mapping between Discord roles and GitHub. Teams are read live with one GraphQL query per `/find-work` through the teams token, since a fine-grained token needs the Members permission to list them and that token already has it. Excluded `/grant-access` teams, and every team nested under them, are ignored because admin teams tend to reach every repository. The query fetches each team's ancestor chain, so the exclusion holds at any depth without waiting for the hourly team cache. If the read fails, the draw goes ahead from the whole pool and says so; a bot with no teams token says that team matching isn't set up instead. Teams and repositories past GitHub's 100-per-page limit are dropped and logged as a warning rather than paged.
- **Review suggestions fall back to team repositories.** History matching alone leaves most members with nothing to review. In `pragmatic-papers`, one maintainer wrote about 95% of the human commits on `dev`, and the author is always excluded, so a new volunteer never matches. A pull request that only adds files has no history, so it matches no one at all. When history fills fewer than two slots, the rest come from open pull requests in the member's matched repositories, the same team access the issue draw uses. That costs no extra GitHub reads: the teams query already runs once per `/find-work`, and the open-PR cache already holds every pull request. History matches still rank first because they are the stronger signal. Within the team tier, pull requests nobody is reviewing yet come first, then the longest-waiting. The team read now runs whenever there are open pull requests, not only when the issue pool is non-empty.
- **Bot-authored pull requests are never suggested.** Dependency updates and automated release pull requests (such as a 100-file "Release 2.10.0" into `main`) would match everyone who ever touched `package.json` or any file in the release, and asking a member to review them earns points for no real review. They are dropped when the open-PR cache is built, from GitHub's `user.type` of `Bot`, so neither tier sees them.
- **Claims recorded locally, not inferred from GitHub.** GitHub knows who is assigned but not which Discord member asked or whether it came from the wildcard slot. The GitHub login is denormalized onto the claim so a later relink doesn't reattribute it.
- **Settlement is one transaction guarded on the live state.** The state change and the points award commit together, and the update only matches a row still `claimed` or `requested`, so reruns can't double-pay.
- **Pay only a claimer still assigned at close.** This stops paying someone who dropped the issue and stops paying the original claimer when someone else took it over.
- **Pay only for a close that came from the claimer's own code.** The payout reads the issue's latest close event and pays only when its closer is a merged pull request the claimer authored or a commit the claimer wrote. Without this, anyone able to close issues could claim one, close it and be paid, and a claimer could be paid for someone else's fix. It costs one GraphQL read per closed claim, and an issue closed by hand after an unlinked merge expires instead of paying.
- **Claim before assigning.** The claim row is inserted first and the one-live-claim index decides a race between two members; the claim is withdrawn if the GitHub assignment doesn't land. The re-read before assigning is one REST read of the issue; the GraphQL closer lookup is only for the payout job.
- **A GitHub failure isn't a refusal.** The access check answers assignable, not assignable, or error, so an outage isn't reported to the member as missing access. An assignment that errors may still have landed (a timeout after GitHub applied it), so the bot re-reads the issue before withdrawing the claim. If that read fails too, it keeps the claim and says so, and the payout job expires the claim once the grace period is over if the member was never assigned. Withdrawing it instead could leave an assigned member with nothing to be paid on.
- **Fresh claims get a grace period.** Because the claim is recorded before the assignment, a payout run can land in between and see the claimer unassigned. A claim under 10 minutes old is left alone in that state instead of expired.
- **Claims age out.** Issue claims expire after 30 days and review requests after 14, so the payout job's GitHub reads don't grow without bound as work is abandoned. The windows are constants in `find-work-payout-service.ts`. An issue claim that ages out also unassigns the claimer on GitHub: the claim is recorded and assigned together, but expiry only touched the bot's record, so the issue stayed assigned and out of the pool (which takes only unassigned issues) for good, and nobody, the claimer included, could claim it again. It costs one GitHub call per aged-out claim. A failed unassign is logged and the claim expires anyway, rather than retrying forever.
- **Each record settles on its own.** Every claim and review request is settled inside its own error handler, so one bad row can't hold up everyone else's payout for that run.
- **Unreadable status means wait.** If GitHub can't be read, the claim is left for the next run instead of expired.
- **Acknowledge the press before calling GitHub.** Claiming makes up to three GitHub requests, each with a 10-second timeout, well past Discord's 3-second window for answering a button. The press is deferred first and the reply edited once the outcome is known.
- **Ephemeral reply with a five-minute button window.** A draw is personal, and an ephemeral reply keeps channels clean. The cost is that buttons stop working when the interaction expires.

## Risks / Trade-offs

- A null `state_reason` on a closed issue is treated as completed, since that is what GitHub records when no reason is given. Because a close must also come from a merged pull request or commit, this no longer lets a careless or self-made close pay out.
- A pull request that fixes an issue without a closing keyword (`Fixes #n`) leaves the claim to expire when someone closes the issue by hand. The `/find-work` reward line tells members their own merged pull request has to close the issue.
- Work that lands through someone else's pull request doesn't pay: for example, when a maintainer opens the pull request for the claimer, or the claimer only co-authored its commits. The same goes for a closing commit whose author email isn't tied to a GitHub account. Those claims expire, and a lead can award the points by hand.
- A claim still unfinished after 30 days expires unpaid, even if the member finishes it later. The bot unassigns them, so the issue returns to the pool and anyone, including them, can claim it again, which starts a fresh 30 days. A member partway through slow but real work loses the assignment; letting them renew is deferred until that comes up.
- A pull request merged into a branch other than the repository's default doesn't close the issues it references, so a claim on such an issue never pays. No public repository in the org has this setup today: each one that keeps two long-lived branches makes the integration branch (`dev` or `develop`) the default. Revisit if a repository moves to a non-default `dev`.
- Review timestamps from GitHub are compared with a one-minute allowance for clock skew → a review submitted just before the request could count. Accepted as negligible.
- Point amounts are capped at 10 per payout in config validation to catch typos that would swamp the leaderboard, and unknown keys under `points` stop startup so a misspelled key can't silently pay the default. The parsed amounts are frozen; the command and the payout job take them as a constructor argument, so tests pass their own instead of changing the shared config.
- A claim kept because its assignment couldn't be confirmed holds the issue for up to about an hour if the assignment never landed.
- The team tier widens who can earn review points: any member on a team that reaches a repository can take a review there, and any submitted review pays, including a one-line comment. This was already true of history matches. One live request per member per pull request, and no re-suggesting a past reviewer, keeps it to one payout per pull request per member. Leads can lower `review` points if low-effort reviews become a problem.
- Accepting `good first issue` and `help wanted` puts issues labelled before `/find-work` existed into the pool, and some may be stale or no longer wanted. They are still issues a person chose to advertise, and the wildcard's lean toward the stalest third will surface them; maintainers can remove the label, list the repository in `excludeRepos`, or narrow `markerLabels`. Anyone with triage access can now opt an issue in by applying a common label, which was already true of `available`.
- Release pull requests opened by a person rather than a bot are still suggested. Excluding pull requests that don't target the default branch would catch them, but would also hide stacked pull requests, which do want review.
- Central files that nearly every change touches (in this repo, `src/start-bot.ts`, `src/commands/metadata.ts` and `lang/lang.en-US.json`) dominate history ranking, so a member who registered many commands can outrank one who wrote the service a pull request actually changes. Weighting matched files by how rarely they change would fix this. It is deferred until real suggestions look noisy.
